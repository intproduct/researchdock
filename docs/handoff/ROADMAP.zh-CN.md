# v0.2 路线图与任务边界

目标：先成为可用的个人/小团队跨设备科研项目管理工具，再增加受控同步和科研集成。14–25 传统人日只是先前下一阶段范围的粗估；下表包含进一步细化和后续扩展，不代表每项已经估时、设计或授权。

仅 T01/T02 有完整执行任务卡。以后每包在进入实施前补齐数据/API/验收契约，不把下表一句话当作完整规格。

| ID | 任务 | 主要验收结果 | 依赖 / 分工建议 |
| --- | --- | --- | --- |
| T01 | 项目修订历史 | 原子快照、基线回填、冲突保留草稿 | 当前 ready；Kimi 实现，Codex 审计 |
| T02 | PostgreSQL/Compose/恢复 | 真正 PG 测试、容器联调、空库恢复 | T01；Kimi 实现，Codex 审计 |
| T03 | Repository 身份及项目关联 | 一个项目多仓库、明确绑定、不按路径误合并 | T02；Codex 先定数据契约 |
| T04 | GitHub 凭据与连接 | 最小权限、可撤销、秘密不回显、不入库明文方案 | T03；先确认个人使用的授权方式 |
| T05 | 远端观察与刷新 | 分支/SHA/观察时间、限流/失败可见、区分缓存 | T04；Kimi 实现，可先手动刷新避免过早上队列 |
| T06 | 比较证据协议 | 明确共同历史所需信息和不足返回 unknown | T03/T05；Codex 设计并重点审计 |
| T07 | 跨副本比较界面 | 两台机器版本关系有证据、dirty 和过期分别展示 | T06；Kimi 实现 |
| T08 | Agent 后台运行 | Windows/Linux 启停、日志轮转、重复实例控制 | T02；Kimi 实现，真实双平台验证 |
| T09 | Agent 配对和故障恢复 | 凭据存储改进、退避、配置诊断、撤销后明确状态 | T08；安全方案先审查 |
| T10 | 独立研究日志 | 决策/问题/结果追加记录、来源、导出 | T01；与状态快照区分，Kimi 实现 |
| T11 | 只读同步计划 | 展示动作、前提与冲突，无远程写入 | T06/T07；Codex 定契约后实现 |
| T12 | 受控同步执行 | 检查点、幂等、失败恢复、操作审查 | T11；高风险独立阶段，不由只读 Agent 顺手扩展 |
| T13 | 导入与科研产物 | 按真实使用选择非 Git 导入、DVC 或投稿快照之一 | 用户优先级决定；拆包，不一次接入所有工具 |
| T14 | 云上线验收 | 用户服务器 HTTPS、备份计划、监控和恢复演练 | T02 + 已选上线功能；真实资源准备后执行 |

T03–T10 与 T14 是后续实用化候选；T11–T13 属于更大扩展范围，不能把其费用算进“只做完首批两包”的承诺。MLflow、Zotero、远程计算和通用知识图暂不实施。

首批两包之后根据实际费用与缺陷率分工：常规模块继续 Kimi；需要复杂一致性/版本语义的部分先由 Codex 缩小并固定契约。实现者不能自行用新框架替换现有 FastAPI/React/SQLModel 栈。
