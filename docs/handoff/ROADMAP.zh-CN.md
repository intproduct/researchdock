只有完成了对应验收才称达到该里程碑。“T07 之后”不是天然可上线，“T14 全部完成”也不要求所有可选功能完成。这里不给基于 Agent 编码速度推算的一周保证；网络、迁移、双平台和恢复验收是独立的实际工作。

## T14 拆分：可以提前准备云端入口

**T14a 云运行基础**：T02 accepted 后即可编写任务卡并选定实施；无需等 T04–T13。范围为实际部署的 HTTPS 入口、最小端口暴露、secrets 配置、持久卷、备份计划及保留策略、恢复运行手册、基本健康/磁盘监测和资源限制。Agent 现有约定要求远程连接 HTTPS，不能为了试用关闭证书验证或放开明文公网登录。没有域名/证书时继续走 T02 的回环端口 + SSH 隧道试验路径。

**T14b 版本上线验收**：在本次选择上线的功能完成后执行。记录发布 SHA/镜像、部署/迁移/回退边界；使用两个真实设备验证关键流程；从实际生成的备份恢复并检查权限；确认重启及网络中断后的表现。数据库模式可能不支持无损回退，不能把切回旧镜像当完整回滚方案。

2 核 2GB 现有服务器先作为受限验证环境：独立 Compose 项目，保留其他容器，串行构建，不先引入额外基础设施。是否扩容依据实际峰值内存、响应和备份窗口再决定，不把扩容作为写任务卡的前提。

## 建议执行顺序

1. 补 T02 远端验收并整合；按 T03 任务卡实施和审计，达到 M1。
2. 需要直接跨网络长期使用时，先安排 T14a；需要先看到 GitHub 时推进 T04→T05→T06→T07。两者可按资源条件调整。
3. 推进 T08→T09，完成 T14b，达到 M3；如果后台驻留比 GitHub 更急，T08/T09 可以提前到 T03 后。
4. 日常使用反馈决定 T10、T11、T13 的先后。只有只读计划可靠且用户明确需要自动写入，才设计 T12。

## 交付、验收与成本纪律

每包保持“契约 → 实现 → 必要自测 → 独立审计 → 修复 → accepted → 整合”。后续任务卡必须明确兼容窗口、增量迁移、权限、失败行为、真实环境矩阵；不能只写功能名称就开始编码。外部服务具体 API/权限在对应任务设计时查官方文档，不在本路线图中虚构验证结果。

审计发现代码问题先修最小范围；环境未验证则单列 blocked_environment。真实密钥留在本机/服务端受控配置，报告只记去秘密证据。没有新增变化或疑点不重复重跑全量检查；本机 Docker 不再尝试，容器在远端验证。

成本按“被验收工作包”记录设计、实现、审计、返工总量。T01/T02 的已有多轮返工说明只比较一次生成速度不足以估总成本；后续以实际账单/usage 为准，未知写 unknown，不用行数或传统人日转换 token。功能卡可以按上述里程碑拆小，但不能删掉数据保护和验证来换取表面完成。
