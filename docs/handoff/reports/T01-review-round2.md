## R1 续项 · P1：旧缓存内容与新 revision 组合，可覆盖刚保存的状态

位置：[Workspace.tsx](../../../frontend/src/research/Workspace.tsx)，`save.onSuccess` 的 499–509 行；关联 `values` 与 `submit` 的 535–554 行。

本轮新增了对提交内容与当前草稿的比较，可以保留请求发出后的输入。但当草稿等于提交内容时，回调仍立即清空草稿，同时将 `baseRevision` 设为 `saved.revision`；`project` 则继续来自尚未刷新完成的查询缓存。此时表单回退到缓存中的旧字段，再次点击保存会把旧字段和新的版本号一起提交，后端正常接受并覆盖最新进展。这不只是界面短暂闪烁。

首轮 R1 已要求同时处理提交结果和查询缓存，避免旧缓存与错误版本。本轮只有 `invalidateQueries`，没有把成功响应的项目状态应用到界面；失效标记不等于刷新已经完成。

### 独立浏览器复现及证据

使用本轮生产构建、一次性 SQLite、测试账号和隔离端口 8027。测试服务外层延迟请求，未修改产品代码。

1. 先完成保存期间继续输入及第二次保存，项目稳定在 revision=3，内容为 `R1_NEW_INPUT_REVIEW2`。

3. PUT 成功产生 revision=4。列表 GET 仍在等待时，输入框却回退为 `R1_NEW_INPUT_REVIEW2`，当前修订仍显示 3，而历史列表已经出现修订 4；保存按钮已可点击。
4. 不修改输入框，再次点击“保存进展”。服务端实际收到 `revision: 4` 加旧文本 `R1_NEW_INPUT_REVIEW2`，PUT 返回 200。

### 最小修复范围与验收

本轮继续聚焦项目详情保存状态，不扩大功能范围：

- 在清空已提交草稿前，让当前项目数据反映 PUT 成功返回的 `saved` 状态，例如安全更新对应项目的查询缓存；保留请求期间的后续草稿。
- 处理已在途的旧查询结果，防止其覆盖较新的保存结果。草稿内容、显示内容与下一次提交使用的 revision 必须一致。
- 若采用等待刷新策略，刷新延迟/失败期间也不能清空已保存内容并开放基于旧数据的保存。仅增加延时或只调用 invalidate 不构成修复。
- 添加确定性的慢 GET 回归：PUT 成功后阻塞项目列表刷新，表单应保持刚保存内容；再次保存不能把旧内容写回；开始新编辑不能错误固定到旧 revision。随后放行刷新，界面仍应一致。
- 同时保留已通过的“PUT 等待期间继续输入，成功后再保存”用例，以及 409 保留草稿检查。不要改变 API 相同内容 PUT 仍递增 revision 的既有契约。
